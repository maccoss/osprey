## Bug Fixes

- **Carafe's per-peptide `_pepNNNNN` pseudo-protein accessions are stripped at library load**: Carafe emits one synthetic accession PER PEPTIDE (`sp|O95139_pep00019|NDUB6_HUMAN`), so every peptide became its own protein — 759,805 distinct accessions collapsing to 42,592 real ones on the 3-file Stellar entrapment library. The damage was not confined to the protein report: second-pass `protein-compact` q-value estimation builds its stratum from proteins with >= 2 *detected* peptides, and a protein owning exactly one peptide can never qualify, so the stratum collapsed, nothing recompeted, and every reported q-value was the carried-over first-pass value with nothing in the output saying so. The manifest's `proteins` column (see v26.6.0) already carried clean accessions, but the only path that applies it is the library-supplied-decoy path, which also hard-fails when the library holds no decoys — so a Carafe library searched with *generated* decoys had no route back to real accessions at all. Stripping at load closes that for every mode; on a manifest run the manifest still wins where it genuinely disagrees. Applied on both the fresh-parse path (before deduplication) and the `.libcache` path. Entrapment and decoy markers are preserved — only the `_pep` + digits token is removed, so `sp|Q9ULK4_p_target_pep00052|MED23_HUMAN_p_target` becomes `sp|Q9ULK4_p_target|MED23_HUMAN_p_target`. Mirrors the C# Osprey `CarafeProteinIdNormalizer` (ProteoWizard/pwiz#4573); the two implementations are validated in cross-impl parity at 1e-9 on `StellarLibraryDecoy`. **Note**: the strip assumes the default `--pep-suffix-format` (`_pep{:05d}`) of `scripts/build_entrapment_peptide_fasta.py`; a library built with a custom format is not recognized.
- **Library-decoy pairing no longer gives two decoys one entry_id**: the manifest pass bucketed library entries by the manifest's `peptide_type`, not by whether the library entry was a decoy. Carafe can merge a decoy with an identical real target into one row whose ProteinID starts `decoy_`; the prefix scan marks that row a decoy, but the manifest lists its sequence as a `target`, so its paired decoy copied an id that already carried the decoy bit. Per-file deduplication then kept one of the two, one entry_id carried two peptides, and first-pass FDR aborted hours into a large run (82 files, SEA-AD 07-27 library: 35 such rows, e.g. `AQLKDTR` z2 against its reversed decoy `TDKLQAR`). A decoy is now never placed on the target side of a manifest pair, and the load fails listing every row where the library and its manifest disagree, so the library can be regenerated. A second check after pairing refuses the library if any two decoys still share an entry_id, listing every group. The `.libcache` stores the library before pairing, and pairing reruns on every load, so no cache version change is needed. Mirrors ProteoWizard/pwiz (`DecoyPairingManifest.ApplyToLibrary`, `LibraryDecoyPairing.FindSharedDecoyIds`).
- **Generated decoys keep both modifications that share a residue**: the library loaders put an N-terminal modification on residue 0, where a modification of the first residue also sits (`(UniMod:1)M(UniMod:35)`), and the target's fragments carry both. `recalculate_fragments` built its per-position mass map with `insert`, so the second modification replaced the first and every decoy fragment spanning that residue was one modification light - 42 Da for an N-terminal acetyl. The masses at one position now add. Only libraries with such entries change; none of the regression libraries has one. Mirrors ProteoWizard/pwiz (`DecoyGenerator.RecalculateFragments`, which now sums through `PeptideFragmentMass.ModMassesByPosition`); the regression test is the Rust twin of `DecoyConstructionTest.DecoyFragmentCarriesStackedModifications`.
