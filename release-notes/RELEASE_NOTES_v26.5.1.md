# Osprey v26.5.1 Release Notes

Headline patch: pass-1 calibration now correctly applies the auto-detected library→mzML RT bridge so libraries that emit retention time in seconds (notably current Carafe builds with `Tr_recalibrated` in seconds) no longer produce 0 calibration matches against minutes-keyed mzML files. Three cross-implementation correctness fixes for `.blib` / mzML / FDR-sidecar parity with OspreySharp ride alongside, plus the Stage 6 cross-implementation diagnostic dumps and `--join-at-pass=2` Stage 7 entry-point scaffolding that landed after v26.5.0 was tagged. Build requirement note: `flate2` now uses the `zlib-default` backend (vendored stock zlib via `libz-sys`) instead of the Rust `miniz_oxide` default — this adds a C compile step to the build but produces `.blib` deflate output bit-compatible with Skyline's existing writer.

## New Features

- **`--join-at-pass=2` enters the pipeline at the post-Stage-6 boundary** for fast Stage 7 (protein FDR + blib output) iteration. Consumes reconciled `.scores.parquet` + `.{1st,2nd}-pass.fdr_scores.bin` sidecars from a previous straight-through Stages 1-6 run and runs only the second-pass q-value recompute, protein parsimony, picked-protein FDR, and blib output. On Stellar 3-file this drops the Stage 7 edit-build-test cycle from ~1:27 to ~0:07. Bit-parity with the in-process pipeline is validated by `Compare-Stage7-Rehydration.ps1`, which SHA-256-compares the Stage 7 dump between `--join-at-pass=1` (full pipeline from Stage 4 input) and `--join-at-pass=2` (rehydrated from the same run's reconciled output) — currently byte-identical on Stellar. The `--no-join` and `--join-only` modifiers are explicitly rejected (Stage 7 is the final join, no per-file phase follows it). New `expect_reconciled_input` config gate refuses raw Stage 4 parquets up front so a misconfigured invocation can't silently re-run the full pipeline. The strict gate is paired with a metadata-only parquet rewrite at the end of every reconciliation pass (even when no overlay rows are produced) so the operator's previous-run output is always recognized as Stage-6 reconciled.

- **`OSPREY_DUMP_STAGE7_PROTEIN_FDR` cross-impl bisection dump for second-pass picked-protein FDR.** Emits one row per protein group at the end of the second-pass picked-protein FDR computation: `accessions`, `n_unique`, `n_shared`, `best_peptide_score`, `group_qvalue`, `is_target_winner`. Sort key `(is_target_winner DESC, group_qvalue ASC, accessions ASC)` — target winners (which drive FDR calibration) at the top of the file. The numeric `group_id` is **omitted** because `build_protein_parsimony` assigns it in HashMap iteration order; joining on the sorted-accessions string instead keeps the dump diff-stable across runs. Symmetric with `OSPREY_DUMP_PROTEIN_FDR` (first-pass) added in v26.5.0. Gated by env var; `OSPREY_STAGE7_PROTEIN_FDR_ONLY=1` exits after writing for fast bisection cycle.

- **Stage 6 cross-impl bisection diagnostics: `OSPREY_DUMP_RESCORED`, `OSPREY_DUMP_CWT_PATH`, plus `run_protein_q` column on `OSPREY_DUMP_PERCOLATOR`.** Three-tier observability over the Stage 5 → Stage 6 worker rehydration seam. `OSPREY_DUMP_RESCORED` writes `rust_stage6_rescored.tsv` at the high-level post-rescore boundary (same shape as the Stage 5 Percolator dump but fires AFTER the per-file rescore loop completes — catches Stage 6 output divergence before drilling into per-call dumps). `OSPREY_DUMP_CWT_PATH` writes per-`(file, entry)` CWT path summary including `n_cwt_peaks`, `n_final_peaks`, `n_scored`, `scored`, `sigma`, and three consensus-signal scalars (`consensus_l1`, `consensus_max_abs`, `consensus_argmax`) computed inline from the XICs. The existing `OSPREY_DUMP_PERCOLATOR` gains a `run_protein_q` column between `run_peptide_q` and `experiment_precursor_q` so the v3 sidecar's persisted protein q-values flow through the cross-impl diff. `dump_stage5_percolator` now also fires from `rescore::run_rescore` so a `--join-at-pass=1 --no-join` worker run produces the same dump as the in-process pipeline. Validated against OspreySharp on Stellar 3-file: 7/7 columns × 1,388,872 rows × max_diff=0 at the worker entry seam, 7/7 columns × 392,029 rows × max_diff=0 at the post-rescore seam.

## Bug Fixes

- **mzML loader now sorts spectrum centroids at load time.** Some Astral mzML files contain occasional non-monotonic centroid pairs (~0.07% of MS2 spectra observed on a HeLa Astral 3 m/z DIA file). Osprey's downstream fragment matching binary-searches the spectrum via `partition_point`; on an unsorted region this returns one position while the OspreySharp port's `BinarySearchLowerBound` (different step pattern) returns another, producing UB-style cross-impl divergence on the affected scans. Fixed by detecting any centroid inversion at parse time and sorting with a stable permutation so every consumer sees a well-defined ordering. Bumped the `.spectra.bin` cache format `VERSION` from 1 to 2 so caches written by the old parser are invalidated and reloaded through the sorting path. Single-file zero-inversion mzML files take the fast path (an `is_sorted` check) with no behavior change.

- **`flate2` dependency switched to `zlib-default` backend for cross-impl `.blib` byte parity.** The default Rust `miniz_oxide` backend produces RFC-1950/1951-valid deflate output, but makes different huffman-table / end-of-block choices on small inputs than stock zlib — and the canonical BLIB writer convention (ProteoWizard's `pwiz_tools/BiblioSpec` C++ writer, plus Skyline's `Model/Lib/BlibData` writer via DotNetZip's Ionic.Zlib level 6 since 2009) targets stock zlib. With this change plus OspreySharp's switch to Ionic.Zlib, `Compare-Blib-Crossimpl.ps1` returns OVERALL: PASS on both Stellar 3-file (45,153 RefSpectra) and Astral 3-file (129,352 RefSpectra), including the previously-mismatching `RefSpectraPeaks` blob bytes. Build requirement note: this routes through `libz-sys`, which uses a vendored stock zlib (no system zlib install required) but does add a C compile step to the build. CI gates (`cargo fmt --check`, `cargo clippy -D warnings`, `cargo test --workspace`) all pass with the new backend with no test changes.

- **FDR sidecar loader now matches records to stubs by `entry_id`, not by position.** The strict `header_count == entries.len()` guard silently degraded multi-file `--join-at-pass=2`: the reconciled parquet load grows to the post-rescore + gap-fill row count, but the 1st-pass sidecar was written pre-gap-fill and the 2nd-pass sidecar post-compaction. Both counts are smaller than the parquet load, so the loader rejected both sidecars and the pipeline fell through to retraining Percolator from scratch on the wrong input set (the post-rescore parquet rather than the post-compaction subset the original 2nd-pass scored), drifting Stage 7 protein FDR vs the straight-through pipeline. Fixed by switching the loader to `entry_id` lookup: callers may pass a superset of the sidecar's entries (entries with no matching record keep their default Score=0, q=1 values), but a sidecar record whose `entry_id` is not in the caller's stubs is still rejected as corruption so a stale or wrong-parquet sidecar surfaces clearly. Single-file degenerates to a 1:1 lookup with no perf cost vs the previous positional walk. Matching C# fix shipped in the OspreySharp parity branch.

- **Calibration pass-1 now applies the auto-detected library→mzML RT bridge.** When library RT and mzML RT are on visibly different axes (e.g., a Carafe library with `Tr_recalibrated` in **seconds** searched against an mzML in **minutes**), Osprey's calibration discovery correctly detects the mismatch and computes a linear bridge, but the pass-1 scoring call was passing `expected_rt_fn = None` — so the RT prefilter was comparing raw library RT (e.g., 174.78 sec) against spectrum RT in minutes within a tolerance that can't bridge the ~60× gap. Every candidate failed the prefilter and the calibration retry loop blew through all three escalations finding `0 confident peptides` before falling back to the configured `fallback_rt_tolerance`. After fallback, every Astral-style HRAM search with a seconds-encoded library was effectively running with no calibrated RT model. Fixed by hoisting the `linear_rt_mapping` closure out of the per-attempt loop and passing it to the pass-1 scoring call when `use_linear_mapping = true`. Libraries that already use matching units (minutes-vs-minutes; identity mapping) retain bit-identical pass-1 behavior to before — `expected_rt_fn` is only set when the unit auto-detect fires. The RT-mapping decision logic was also extracted into a unit-tested `compute_rt_mapping` function so future refactors can't silently drop the bridge again. Seven regression tests in `pipeline.rs` cover identity, seconds-to-minutes (Carafe), iRT-to-minutes (Biognosys), disjoint-minutes, degenerate zero-range, and the strict `< 2×` range-ratio threshold.

- **`lib_cosine` counting features now survive precursors with fewer than 2 library fragments in the spectrum's m/z range.** The shared early-return at `lib_preprocessed.len() < 2` zeroed all counting features (`n_matched`, `consecutive_ions`, `explained_intensity`, `fragment_coverage`, `sequence_coverage`, `base_peak_rank`, `top6_matches`) when the cosine score itself was correctly undefined. But those features depend only on the `matches` returned by `match_fragments` (which scans the full library regardless of in-range count) and were already correct before the bail. Concrete impact: a peptide with most library fragments below the DIA detector's m/z floor — only one fragment in range, matched — got `consecutive_ions=0`, `explained_intensity=0` instead of `1` and the matched-intensity fraction, inflating FDR cost for affected entries. Fixed by merging the in-range count into the existing `cosine_ok` gate (alongside the norm check) so cosine / Pearson / Spearman gate uniformly while counting features fall through. Surfaced via cross-impl Stage 6 byte-parity validation against OspreySharp on Astral: 6 decoy rows diverged on `consecutive_ions` / `explained_intensity` before the fix; both Stellar and Astral PASS end-to-end after.

- **`--join-at-pass=2` error messages now reference the actual pass.** Pre-fix, `validate_hpc_args` hardcoded `--join-at-pass=1` in the `--input` / `--input-scores` / `--library` / `--output` validation errors, but `args.join_only` is true for both `--join-at-pass=1` and `--join-at-pass=2` after `normalize_hpc_args`. A misconfigured `--join-at-pass=2` invocation surfaced diagnostics that quoted the wrong flag, sending the user to the wrong fix. Now derives the actual pass from `args.join_at_pass` and templates it into the error text.

- **`--join-at-pass=2` rehydration: protein-FDR + compaction now run under the cached fast path.** When all parquets are `ValidReconciled`, the existing skip-Percolator optimization gates first-pass protein FDR and protein-aware compaction behind `if !can_skip_fdr`, leaving `run_protein_qvalue` at its default 1.0 and letting the second-pass picked-protein FDR see a different (pre-compaction) pool than the straight-through pipeline does. Observed effect on Stellar 3-file: ~6500 vs ~6200 protein groups depending on which entry path produced the output. Fixed by running both unconditionally when `expect_reconciled_input` is set, regardless of the skip-Percolator gate.

- **`--join-at-pass=2` rehydration: FDR sidecar load order now matches the score-pass each stage needs.** First-pass protein FDR + compaction need q-values derived from 1st-pass scores; the post-compaction recompute needs 2nd-pass scores. The default sidecar load preference (2nd-pass first, fall back to 1st-pass) loaded the wrong scores during compaction. Fixed by inverting the preference for `--join-at-pass=2`: load 1st-pass first, run protein FDR + compaction, then reload 2nd-pass after compaction so the second-pass q-value recompute uses the right rank ordering. The implementation tuple-binds the `(primary, fallback)` pair once per file to avoid clippy's `if_same_then_else` false-positive on the two structurally-identical (but order-of-evaluation-different) load arms.

- **`--join-at-pass=2`: trust the persisted q-values, skip the recompute.** The v3 FDR sidecar carries the post-second-pass q-values directly (not just SVM scores), so calling `compute_fdr_from_stubs` to re-derive them is a no-op at best and a source of drift at worst — in particular, the straight-through pipeline skips the second-pass FDR recompute entirely when `total_rescored == 0`, so its `2nd-pass.fdr_scores.bin` contains first-pass-derived q-values that `compute_fdr_from_stubs` would re-derive against 2nd-pass scores. Now skipped under `--join-at-pass=2` to give bit-identical output to the persisting run.

## Performance

- **Stage 7 fast-iteration cycle: ~12× speedup via `--join-at-pass=2`.** Re-running Stage 7 (protein parsimony + picked-protein FDR + protein report + blib output) now consumes reconciled parquets directly from a previous Stage 1-6 run instead of re-running the entire pipeline. On Stellar 3-file the Stage 7 edit-build-test cycle drops from ~1:27 (full pipeline rerun) to ~0:07 (rehydrated). The use case is iterating on protein-FDR parameters or `--shared-peptides` mode without paying the Stage 1-6 cost on each iteration.
