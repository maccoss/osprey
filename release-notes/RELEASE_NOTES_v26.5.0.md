# Osprey v26.5.0 Release Notes

Cross-implementation parity release. Headline items: a new HPC fan-out mode (`--join-at-pass=1 --no-join`) externalizes the previously-sequential Stage 6 per-file rescore so it can run as one Slurm/PBS array job per file, with bit-parity to the in-process flow validated by `Compare-Stage6-Worker.ps1`; the `--join-at-pass=<N>` CLI replaces the bare `--join-only` flag with explicit pass-numbered modes; new `<stem>.reconciliation.json` boundary file plus a v3 `<stem>.1st-pass.fdr_scores.bin` sidecar (now carrying `run_protein_qvalue`) form the Stage 5 → Stage 6 fan-out seam, designed for byte-identical output between Rust Osprey and OspreySharp; eleven env-var-gated diagnostic dumps localize cross-impl divergence at every pipeline seam; and four real determinism / numerical-correctness bug fixes (PEP non-determinism, grid-search tie-break, Gauss-Jordan partial pivoting, RT calibration JSON f64 round-trip).

## New Features

- **Stage 6 per-file rescore worker (`--join-at-pass=1 --no-join`).** New HPC mode that runs Stage 6 (per-file rescore + gap-fill + reconciled parquet write-back) as an embarrassingly-parallel fan-out, consuming the boundary file pair (`<stem>.1st-pass.fdr_scores.bin` + `<stem>.reconciliation.json`) persisted by `--join-at-pass=1 --join-only`. The worker hydrates the in-memory state at the Stage 5 / Stage 6 seam, applies the same compaction predicate the in-process pipeline uses (`run_peptide_qvalue ≤ peptide_gate OR run_protein_qvalue ≤ protein_gate`), and drives the same `rescore_per_file_loop` that the in-process pipeline calls. Bit-parity with the in-process flow is enforced by `Compare-Stage6-Worker.ps1` (3/3 PASS on Stellar across all 40 columns × 463k rows). Together with `--no-join` (Stages 1-4) and `--join-at-pass=1 --join-only` (Stage 5 only), this completes the four-step HPC orchestration: per-file scoring → first join → per-file rescore → final join. See [docs/18 — HPC Scoring Split](docs/18-hpc-scoring-split.md).

- **`--join-at-pass=<N>` CLI surface for HPC orchestration.** Replaces the bare `--join-only` flag with an explicit pass-numbered surface so each fan-out / fan-in seam in the pipeline has its own well-named mode. `--join-at-pass=1` runs Stages 5-8 from per-file `<stem>.scores.parquet` outputs (the legacy `--join-only` semantic). The `--join-only` and `--no-join` modifiers narrow it further: `--join-at-pass=1 --join-only` runs Stage 5 only and writes the boundary file pair; `--join-at-pass=1 --no-join` runs Stage 6 only and consumes the boundary files. `--join-at-pass=2` is reserved for future Stage 6 → Stage 7 fan-back-in. The legacy bare `--join-only` flag is rejected with a directional error pointing to `--join-at-pass=1 --input-scores ...`.

- **Stage 5 → Stage 6 boundary file persistence.** New `<stem>.reconciliation.json` boundary file alongside each parquet, written at the end of Stage 5 by `--join-at-pass=1 --join-only` (or by the in-process pipeline when fan-out is enabled). Carries the planner's non-Keep `ReconcileAction`s split into two homogeneous arrays (`use_cwt_peak_actions` / `forced_integration_actions`), per-file `gap_fill_targets`, and the refined per-file LOESS RT calibration. Field order is alphabetical at every nesting level so Rust's `serde_json::to_writer_pretty` and C#'s `Newtonsoft.Json` produce byte-identical output. Numeric values route through a shared `format_f64_roundtrip` helper (single canonical fixed-point decimal form) on both sides. Schema-versioned (`format_version: 1`) with `serde(deny_unknown_fields)` on every struct so cross-impl drift fails fast. The matching `<stem>.1st-pass.fdr_scores.bin` sidecar was bumped to v3 (record 52 → 60 bytes) to add `run_protein_qvalue` so the Stage 6 worker can apply the same protein-rescue compaction predicate the in-process pipeline uses. See [docs/12 § Reconciliation Boundary File](docs/12-intermediate-files.md#5-reconciliation-boundary-file-stemreconciliationjson).

- **`OSPREY_DUMP_RECONCILIATION` cross-impl bisection dump.** New env-var-gated dump that emits the post-planning reconciliation actions per file, sorted by `(file_name, action_kind, entry_id)` for stable diff. Fires unconditionally on the bisection workflow (no `_ONLY` companion needed since the in-process flow continues past it). Catches drift between Rust and C# planner output before any rescore work is attempted.

- **Stage 6 worker bisection dumps (`OSPREY_DUMP_MP_INPUTS`, `OSPREY_DUMP_PREDICT_RT`).** Two new env-var-gated dumps for ULP-level cross-impl bisection inside the Stage 6 worker. `OSPREY_DUMP_MP_INPUTS` captures the `(frag_pos, frag_idx, scan_idx, rt, intensity)` matrix going into every `tukey_median_polish` call, keyed by `(entry_id, apex_scan)`. `OSPREY_DUMP_PREDICT_RT` captures `RTCalibration::predict()` inputs/outputs plus a once-per-file dump of the cal's `library_rts` / `fitted_values` arrays. Both use `OnceLock<Mutex<File>>` lazy-open + thread-safe append; zero overhead when env-var unset. Workflow notes in the docstrings show the typical sort + diff pipeline.

- **Stage 5 / Stage 6 cross-implementation diagnostic dumps for OspreySharp parity.** Ten env-var-gated TSV dumps localize where the Rust and C# (OspreySharp) ports diverge during a `--join-at-pass=1` run, without affecting production behavior when the gates are unset. Each dump uses an `OSPREY_DUMP_<NAME>` / `OSPREY_<NAME>_ONLY` pair (the second exits the process after writing for fast bisection). Stage 5 covers the Percolator FDR pipeline: `OSPREY_DUMP_STANDARDIZER` (per-feature mean/std), `OSPREY_DUMP_SUBSAMPLE` (subsample membership and fold IDs), `OSPREY_DUMP_SVM_WEIGHTS` (per-fold SVM weights, bias, iteration count), and `OSPREY_DUMP_PERCOLATOR` (per-FdrEntry SVM score, PEP, and all four q-values, before compaction so decoys are present). Stage 6 covers the planning checkpoint: `OSPREY_DUMP_CALIBRATION` (loaded `library_rts` / `fitted_values` per file), `OSPREY_DUMP_PROTEIN_FDR` (first-pass picked-protein FDR per peptide), `OSPREY_DUMP_CONSENSUS` (per-peptide consensus RT and MAD), `OSPREY_DUMP_INV_PREDICT` (per-detection apex_rt / library_rt / sigmoid weight), `OSPREY_DUMP_MULTICHARGE` (per-file rescore targets keyed by stable `entry_id`, not Vec position), and `OSPREY_DUMP_REFIT` + `OSPREY_DUMP_LOESS_FIT` (refined-calibration scalar stats vs. full LOESS curve, for stats-vs-smoother bisection). All numeric columns route through a shared `format_f64_roundtrip` helper that handles NaN/inf and normalizes `-0.0 → "0"` to match .NET BCL G17. Rows are sorted on stable keys (peptide, entry_id, fold_id) so cross-impl comparison scripts hash-join sort-order-agnostic.

## Bug Fixes

- **Fixed PEP non-determinism in first-pass FDR.** `compute_fdr_from_stubs` previously iterated the `targets` and `decoys` HashMaps directly when building the `winner_scores` / `winner_is_decoy` arrays for `PepEstimator::fit_default`. Rust HashMap iteration order is randomized per process, and `PepEstimator`'s internal float sums are not associative, so per-entry PEPs drifted by ~1 ULP run-to-run. Compounding this, `Kde::pdf` used `par_iter().fold().sum()` for the kernel summation — Rayon's work-stealing tree shape is non-deterministic, so the same KDE fit produced ~1-ULP-different bins across calls. Fixed by sorting the union of base_ids before building the winner arrays, and by switching `Kde::pdf` to a serial `iter().fold()` reduction. The performance cost is negligible (≪ 1 second for ~1000 bins × ~241k samples on Stellar) compared to the Percolator SVM training that precedes it. Stage 5 dumps are now byte-identical across runs of the same input.

- **Fixed `grid_search_c` tie-break to match the documented "first C wins" intent.** The grid search used `Iterator::max_by_key`, which per stdlib docs returns the **last** tied element, but the surrounding comment said "first C as tiebreaker" and the OspreySharp port already implemented first-tied. On a tie between e.g. C=1.0 and C=10.0, Rust picked 10.0 while C# picked 1.0 — the higher-C model has more complexity, so per-fold SVM weights drifted between implementations. Replaced with a manual scan using strict `>` so first-tied wins.

- **Fixed `count_passing_targets_svm` internal inconsistency that affected SVM hyperparameter selection.** The grid-search `count_passing_targets_svm` used a conservative `(n_decoy + 1) / n_target` q-value formula, but the sibling `select_positive_training_set` on the same Percolator iteration path uses non-conservative `n_decoy / n_target` (matching the documented `compute_qvalues` helper). The two functions evaluated the same training data against incompatible objectives, causing grid search to pick a different `best_c` from OspreySharp on borderline cases. Switched to non-conservative q-values with the standard backward monotonization pass; conservative q-values are still used for final reported FDR.

- **Guard LDA fit against single-class input.** `LinearDiscriminantAnalysis::fit` previously returned `None` silently when given an all-target or all-decoy label set: the absent-class loop iteration produced a 0-row class matrix whose covariance divides by zero, seeding `scatter_within` with NaN and causing the downstream `Gauss::solve` to return `None`. The caller couldn't distinguish this precondition violation from a genuine numerical failure. Added an explicit guard at the top of `fit` that counts targets and decoys in one pass, names the missing class in the warn-log, and returns `None` before any matrix arithmetic. Calling code (LDA per-fold calibration scoring) now logs the cause instead of a generic "training failed" error.

- **Fixed Gauss-Jordan partial pivoting and tolerance-based singularity checks.** Three correctness bugs in the Gauss-Jordan elimination used by LDA scatter-matrix solves: (1) `echelon` selected the pivot row by **signed** max, so a column like `[-4, 0]` picked the zero pivot (because `0 > -4`) and skipped the large-magnitude negative — partial pivoting fix uses `abs()`; (2) the zero-pivot guard used exact equality `== 0.0` instead of a `1e-12` tolerance, allowing rounding-debris pivots like `1e-18` to produce factors of `1e18` that obliterated the row; (3) `left_solved` used signed off-diagonal comparison `x > 1E-8` (a large negative passed silently), exact-equality diagonal checks (`x != 1.0 && x != 0.0` rejects `0.99999999`), and silently accepted NaN entries — fixed by switching all comparisons to `(x - target).abs() > TOL`, adding an explicit `is_finite` rejection, and requiring zero-rows on the left to have matching zero-rows on the right (otherwise the system is inconsistent). Mirrors fixes landing simultaneously in the OspreySharp port (ProteoWizard/pwiz#4155). Verified locally on Stellar and Astral at 1e-6 with no observable change to current production paths.

- **Fixed RT calibration JSON parser to round-trip f64 values exactly.** `serde_json`'s default fast number parser is not correctly rounded for full-precision f64 — the decimal `1.9140296182650374` parses to `0x3FFE9FDD85606113` under `f64::from_str` and .NET `double.Parse` (the closest representable f64) but to `0x3FFE9FDD85606114` (1 ULP higher) under serde_json's default. `ryu` writes the calibration JSON correctly, but reading back through serde_json drifted at the borderline, breaking byte-parity with OspreySharp on `--join-only` reruns. Added a custom deserializer for the three `Vec<f64>` arrays in `RTModelParams` (`library_rts`, `fitted_rts`, `abs_residuals`) that captures each element via `RawValue` and re-parses through `f64::from_str`. Calibration JSONs now round-trip exactly. Enabled the `raw_value` feature on `serde_json` at the workspace root.

- **Stage 6 calibration refit now honors `OSPREY_LOESS_CLASSICAL_ROBUST` (default on).** `refit_calibration_with_consensus` was building its `RTCalibrator` via the `with_bandwidth` / `with_outlier_retention` builders, which left `classical_robust_iterations` at the struct's `Default::default()` value of `false`. Stage 4's main calibration reads the env-var with default-on semantics, so the same pipeline run was using classical Cleveland 1979 robustness in Stage 4 and the legacy single-refresh algorithm in Stage 6 refit. OspreySharp's Stage 6 also defaults to classical-on, so Rust's refit diverged cross-impl. Switched refit to `RTCalibrator::with_config` and the same env-var read used at Stage 4. Set `OSPREY_LOESS_CLASSICAL_ROBUST=0` to disable.

- **Stage 6 reconciliation gate now fires on `--join-only` multi-file runs.** Both `reconciliation_enabled` checks were `config.reconciliation.enabled && config.input_files.len() > 1`. On `--join-only` invocations driven by `--input-scores` parquets, `config.input_files.len()` is 0, so multi-file `--join-only` runs skipped Stage 6 reconciliation entirely. Switched both gates to the post-load `per_file_entries.len() > 1`, which equals `input_files.len()` for non-`--join-only` runs (no behavior change there) and correctly reflects parquet count for `--join-only`.

- **Reject `--input-scores` without `--join-at-pass` to prevent silent skipped scoring.** Pre-fix, `osprey -i sample.mzML --input-scores cache.parquet ...` would parse, then `run_analysis` would see `config.input_scores = Some(...)` and silently route through the join path, **skipping the user's mzML scoring entirely**. New CLI guard at `validate_hpc_args` rejects the combination up front with a directional error pointing at the mode the user probably meant (`--join-at-pass=1 --input-scores ...` for join, or drop `--input-scores` for scoring). Regression test added.

- **`serde_json` `float_roundtrip` feature enabled at the workspace level.** Even with the `RawValue`-based custom deserializer for `RTModelParams`, the boundary-file calibration arrays travel through default `serde_json` and lost 1 ULP on shortest-roundtrip strings like `"3.1575921556296254"` (default returns bits `0x...878`, correct is `0x...877`). On Stellar this propagated to ~80k 1-ULP-off values per file → ~13.4k rows of `rt_deviation` divergence in `--join-at-pass=1 --no-join` worker output. Enabling the `float_roundtrip` feature (~2× f64 parse cost; negligible vs. SVM training) closes the gap. Regression test in `reconciliation_io.rs` asserts bit-exact round-trip for six known-tricky values with a directional panic message naming the likely cause if it fails.

- **`library_identity_hash` now uses file name only (not full path) and preserves non-UTF-8 names.** The cache-invalidation hash for the spectral library previously included the full filesystem path and would crash on non-UTF-8 file names. Two follow-up fixes: drop the directory portion (so the hash is portable across machines and shared-fs mount points with different parent paths) and use `to_string_lossy()` so non-UTF-8 names hash deterministically rather than panicking. Combined effect: cross-impl `--join-only` runs now produce identical hashes regardless of host filesystem layout.

- **`dump_stage6_reconciliation` fires unconditionally for the bisection workflow.** The dump previously gated on `OSPREY_DUMP_RECONCILIATION` like other dumps, but the bisection workflow needs to capture the planner's output even on a normal run. Removed the env-var gate so the dump always writes when explicitly requested via the post-planning hook; the env-var-gated `_ONLY` companion is retained for fast-exit usage.

## Performance

- **Stage 6 per-file rescore is now embarrassingly parallel under HPC fan-out.** The in-process pipeline processes Stage 6 (spectra reload → boundary-overrides rescore → gap-fill two-pass → reconciled parquet write-back) **sequentially** because each file loads ~3 GB of spectra + full Parquet entries; running it in parallel on a single node would OOM on large experiments. The new `--join-at-pass=1 --no-join` worker mode externalizes that loop: each Slurm/PBS array job rescores one file end-to-end, so 240 files can be rescored on 240 nodes simultaneously instead of one-at-a-time. On a typical multi-replicate experiment Stage 6 is a substantial fraction of total runtime; fanning it out across N nodes gives near-linear speedup until the surrounding fan-in joins (Stage 5 + Stages 7-8) become the bottleneck. Bit-parity with the in-process flow is enforced by `Compare-Stage6-Worker.ps1` (currently 3/3 PASS on Stellar across all 40 columns × 463k rows).

- **Worker compaction action re-keying is O(num_actions) instead of O(num_actions × num_files).** When the Stage 6 worker re-keys reconciliation actions from pre-compaction `(file, vec_idx)` to post-compaction `(file, new_vec_idx)`, it now builds a `file_name → entries` HashMap once up front so each per-action lookup is constant-time. Previously the inner lookup walked the per-file Vec list. Negligible on observed Stellar runtimes (the Stage 6 loop is dominated by spectra I/O and rescoring compute) but eliminates the worst-case quadratic asymptote.
